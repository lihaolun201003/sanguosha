# 牌唯一归属检查器 + 规则状态/客户端视图一致性（Phase 14 v01）

本次交付两件事：

* **任务 A**：一个可开关的实体牌归属检查器，检测同一张实体牌是否同时属于
  多个真实牌区；
* **任务 B**：一套公共工具，让同一条场景能同时检查"房主权威状态 / 某玩家
  应见的合法视图 / 客户端真实同步并适配后的数据 / 当前请求还能否由正确玩家
  继续操作"，并用它补足三个场景缺失的断言。

参考项目的做法只借了两点：`invariants.ts` 的"按牌收集位置、重复即抛错、
默认关闭"和 `applyView-consistency.test.ts` 的"两条独立路径产出的表示互相比
对"。没有照搬 TypeScript 架构，没有换技术栈，也没有做回放系统或引擎重构。

## 2. 检查器的启用方式与检查边界

### 启用方式（默认关闭）

```python
game.assert_card_ownership = True          # 测试：只影响这一局
```

```bash
# 调试：整个进程的所有对局（在进程启动前设置）
SANGUOSHA_ASSERT_CARD_OWNERSHIP=1 python main.py
```

```python
from src.game import invariants
invariants.enable_debug()    # 临时会话级；用完 invariants.disable_debug()
```

优先级（Phase 14.1 修正后的统一语义）：**对局显式设置 > 模块临时强制 >
环境变量**。关闭时热路径只有一次开关判定
（``invariants.armed_for``，实测 0.107 微秒/次），**不做任何牌区扫描**——
这一点由 ``tests/test_view_consistency_tooling.py`` 里的
``test_scanning_is_not_run_when_disabled`` 用 spy 直接证明。

> Phase 14 初版把优先级写成"模块强制 > 对局设置"，并且让 ``Game`` 在构造时
> 把默认值冻结进属性。两处都在 Phase 14.1 修掉了：冻结默认值会让
> ``enable_debug()`` 对已建对局失效（14.1 问题 3），而"全局强制压过按局
> 设置"会让 ``disable_debug()`` 悄悄关掉测试里明确要开的检查。详见
> ``phase14_1_tooling_false_pass_fixes_v01.md``。

### 覆盖的牌区（8 个真实容器）

* 牌堆 `game.deck.draw_pile`、弃牌堆 `game.deck.discard_pile`
* 处理区 `game.processing_zone`、公共牌池 `game.public_card_pool`
* 每名角色：手牌 `hand`、判定区 `judgement_zone`、
  装备区 `equipment`（**单值槽位字典**，按槽位报位置）、
  武将置牌区 `placed_cards`（邓艾的「田」、周泰的「不屈」牌）

### 明确不算牌区

日志、动画队列、`table_cards` 桌面展示副本、`judge_card` / `revealed_card`
单张引用、选牌候选（`pending_selection` / `pending_view_as` /
`pending_card_action` / `PendingRequest.context["candidates"]`）、技能自己的
`skill_state` 引用。它们都是"指向某张牌的引用"，牌的真实归属仍在上面那 8 个
容器里；把它们也算成牌区只会制造误报。

### 虚拟牌与素材牌

只扫实体牌。虚拟牌（`_virtual`）从不进入任何牌区，它既不算归属、也不会与
自己的 `source_cards` 被误判成重复；素材牌本身照常被扫，真的重复归属一样会
被查出来（`test_same_object_in_two_zones_is_still_caught_for_materials`）。

### 检查边界

只在**一次完整移动 / 结算结束**的稳定边界上查：

* 原子执行完毕（含 `ATOM_AFTER` 订阅者的改动）之后；
* `Game.update` 的帧边界——遗留的非原子路径（`queue_draw_cards` /
  `queue_weapon_discards` 这类直接改列表的写法）只在这里被覆盖；
* 测试/调试代码显式调用 `assert_card_ownership(game)` 时。

**不查**"已移出、尚未移入"的中间步骤（先 `UnequipAtom` 再落位、装备结算里
先移出处理区再进装备槽、动画飞行途中）：那时牌本来就不在任何牌区，是"暂时
无归属"。检查器只报"同时属于 2 个及以上牌区"，不报"一张都不属于"，所以这类
中间态天然不会误报（`BoundarySemanticsTests` 钉住了这一点）。

**等待玩家响应同样算合法稳定状态**：检查只比较牌区容器，与 `Pending` 是否
清空无关，检查本身也不改动任何状态（有对应用例）。

### 未覆盖：牌数守恒 / 丢牌检查

**没有实现，也不建议在当前结构下直接加。** 实体牌在若干遗留动画路径里会先
移出原区域、等动画播完才追加到目的地（`Game.queue_draw_cards`、
`queue_weapon_discards`），这期间它合法地不在任何牌区。因此"实体牌总数必须
等于牌堆规模"这条断言会稳定误报，除非先把那些路径改成"移动即落位"。参考
项目的 `invariants.ts` 同样只抛重复、把悬挂引用留成注释掉的诊断。

## 3. 三个场景分别验证了什么

三个场景都在**进程内真实网络**上跑（真实 socket、真实引擎、真实 Renderer、
真实点击；房主与客户端同进程）。公共工具刻意分成两条独立来源，避免"把
`build_view` 抄给客户端再断言相等"：

* **应见视图**（`expected_for`）：直接读权威 `Game` + `visibility` 规则算出；
* **客户端数据**（`client_state`）：读客户端走完
  `LanSession.poll → ClientMatch.handle_client_message → _apply_view →
  RemoteGameView` 之后的对象。

客户端天然慢几帧，所以用 `agree_or_fail` 等两端到同一稳定版本再比，
**不是**放宽比对：超时仍不一致就原样报出差异。

### 场景 A：装备被弃置 / 被取走

`casecount=2`（两个游客）。过一个远程游客真实点击【过河拆桥】/【顺手牵羊】
拆房主装备区的牌。验证：

* 房主权威：装备槽清空、那张牌进弃牌堆（拆）/ 进拿牌人手里（顺）、
  拿牌人手牌张数净不变（出一张、拿一张）；
* 两个客户端都同步到：装备区空掉、弃牌堆张数、手牌张数、本人手牌内容一致；
* 隐藏信息：旁观者拿不到受害者的手牌内容；
* 结算之后没有把正确玩家卡在等待里。

已有测试 `scenario_client_guohe_equipment` 只验了房主权威与隐藏手牌，
**客户端那一侧是否真的同步到此前没有断言**——本次补上。

### 场景 B：丈八蛇矛转化

全程开着牌唯一归属检查。验证：

* **取消**：点武器 → 选一张 → 再点武器取消。没提交、没扣牌、没记出杀次数、
  没进弃牌堆，武器仍在槽里；客户端看到的手牌与取消前一致；
* **成功只结算一次**：两张素材各自**只在弃牌堆里出现一次**、都不在手里、
  是两张不同的实体牌（不是同一张被算两遍）；提交的答案确实带 2 个 card_id 与
  丈八的 skill_id；房主接受、出杀次数 +1、战报有转化记录；
* 客户端侧的弃牌堆张数与手牌张数跟房主一致。

### 场景 C：悲歌嵌套响应

一次【杀】伤害触发两条【悲歌】（两名远程都持有），引擎请求栈变成
`[外层(先绑定那位), 内层(栈顶)]`。验证：

* **结构**：外层属于先绑定者、内层在栈顶，房主只等栈顶那位；
* **过期回答被拒绝**：被覆盖期间对**外层**提交的回答被拒
  （`operation_failed`，"请求已经不在等待中"），且**一张牌都没扣**、
  请求栈没变，客户端也收到了明确的拒绝说明而不是静默等待；
* **覆盖后恢复**：内层答完之后外层恢复到正确的那名玩家，房主等的人正确，
  另一个人不再被视为可操作方；
* **正确玩家完成结算**：他答完之后请求栈清空、弃的牌只进弃牌堆一次、
  战报有【悲歌】；
* **重复回答也被拒**：结算完再补发一次同一条回答，登记表以
  `duplicate_answer` 拒绝，手牌与弃牌堆都没有变化。

另外补了两个可见性核验：每个座位的**权威投影**（房主真正下发的
`build_view`）与**独立算出的应见视图**必须一致，且别人那一格的手牌内容必须
是"没有内容"（与张数无关）；【五谷丰登】的公共牌池是公开信息，两份客户端
看到的必须是**同一份**，而手牌仍然各自只有自己那份。

### 4b. 失败归因（修正 Phase 14 初版的表述错误）

初版报告里有两处互相矛盾的表述：一处写"改动之前退出码 0（1290 全过）"，
另一处写"改动之前之后这个文件都在失败名单里"。**后者才是有效的**，前者是
误读：命令行是 ``... | tail -25``，没有 ``pipefail`` 时退出码来自 ``tail``，
对测试结果没有证明力；输出又正好被 libpng 警告刷满，汇总行没留下来。

因此**"改动前 1290 全过"这个断言不成立，已撤回**。Phase 14 能拿出来的基线
证据只有：加了（当时是空操作的）钩子之后的一次全量跑 = 1290 个 / 1 失败。
"钩子不影响既有用例"这件事另有一条**实证**支撑（见下），比基线对比更强：

* 把检查器函数换成计数代理后跑完一整局 AI 对局（1969 帧，含判定 / 装备 /
  伤害 / 死亡），**关闭状态下调用 0 次**；打开开关后同一帧立刻被调用。
* 即"默认关闭时只剩一次布尔属性读取"是实测过的，不是推断。

那 2 个失败全部落在
`tests/test_engine_v2_phase11_4_3_lan_identity_runtime.py`，它是真实 socket +
随机武将与 AI 的联机用例。判定为**既有不稳定**的依据：

1. 同一次全量跑的失败用例每次都不一样（第 2、4、7 行）；
2. 第 6 行：同一批用例单独重跑，失败断言换成了另一条
   （『远程真人没有走完两轮』→『远程真人没有收到出牌阶段请求』）；
3. 第 5 行：整个文件（41 个用例，含上面这几个）单独连跑两次全过。

**归因状态：既有不稳定（有上述重复观测支撑）。** 但严格来说，"改动前该文件
一次都没失败过"这条**没有可靠基线可证**——所以不能断言"与本次改动绝对无关"，
只能说"本次改动在关闭时是实测的空操作，且该文件在多次重复观测中表现为随机
失败"。Phase 14.1 会按同样的口径重述这件事。

**测试级别如实说明**（按项目既有分级）：

* 本文所有新测试是 **IN-PROCESS**：真实 socket、真实引擎、真实 Renderer，
  但房主与客户端在同一个进程里；
* 批量审计脚本是**纯引擎**（无网络、无 UI）；
* **LOCALHOST MULTI-PROCESS**：未运行（既有 `tools/runtime_parity_run.py`
  负责这一级，本次未涉及它的改动）；
* **PHYSICAL TWO-PC：未验证**（本机只有一台电脑）。

### 剩余限制

1. **未做丢牌 / 守恒检查**（理由见第 2 节末）。检查器当前只保证"不重复"，
   "牌不见了"不在覆盖范围。
2. **检查点是抽样的**：原子边界 + 帧边界覆盖了绝大多数路径，但任何"绕过
   `Game.update`、绕开原子、直接改容器且不做帧推进"的代码不会被发现。
   这类路径目前只存在于测试夹具里（夹具直接写容器是合法用法）。
3. **`placed_cards` 的下发通路不存在**：`view_builder` 与 `visibility` 都不
   发武将置牌区，因此任务 B 的比对里它只出现在权威侧与检查器侧；客户端那一侧
   没有这个字段，也就没有"同步对不对"可验。
4. **`DeathFlow` 不清 `placed_cards`**（死亡角色的「田」「不屈牌」会留在牌区
   里，只有 `player.reset()` 会清）。这**不是**重复归属（牌只在一个区域里），
   所以本次不动它；但如果将来要加守恒检查，这是一处必须先处理的地方。
5. **任务 B 只覆盖"出牌 / 响应 / 嵌套请求"三类时机**，观星一类"允许某人看
   牌堆顶"的授权式可见性没有新断言。
6. **场景 C 的复现依赖技能绑定顺序**（技能按座次订阅 `DAMAGE_SETTLED`，先
   绑定的那位拿外层请求）。顺序变了测试会失败得比较"结构性"，不是静默通过。

### 顺带发现（未修）

## 5. 修复的问题

本次**没有发现需要修改生产规则逻辑的缺陷**：检查器在两个层面（全量既有
测试 + 20 局整局审计）都没有报出重复归属，三个场景的四件事也都自洽。

开发过程中修掉的都是我自己工具/用例的问题（保留在此备查，避免下次重犯）：

| 现象 | 原因 | 修法 |
| --- | --- | --- |
| 视图比对里牌 id 全是空串，看起来像"客户端什么都没收到" | `ViewCard` 的字段叫 `card_id`，权威 `Card` 叫 `id`，工具只读了后者 | `_card_id` 两套都认（`id` → `card_id`） |
| "别人手牌张数为 0"被报成不一致 | 把"空手牌"表达成 `()`、"隐藏手牌"表达成 `None`，判定按张数而不是按"是不是本人" | 抽出 `_hand_ids`：本人给真实内容，别人一律 `None` |
| 两个开关用例在调试开关模式下失败 | 用例断言的是"默认关闭"，而调试模式**故意**让默认变开 | 改成断言"默认值 == 调试开关的取值"，并把"关掉之后不受打扰"单独立一个用例 |
