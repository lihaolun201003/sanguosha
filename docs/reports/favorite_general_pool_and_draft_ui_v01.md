# 「我的武将池」+ 随机候选选将 + 选将 UI 升级（Phase 19）

本机长期偏好（Favorite General Pool）与选将流程 / 界面的改造。规则层没有
新增任何玩法：变的只是"候选从哪来、界面上长什么样"。

---

## 1. 「我的武将池」入口在哪里

主菜单，位于「多人对战（局域网）」与「退出游戏」之间：

```text
开始游戏
多人对战（局域网）
我的武将池        ← 新增（点击进入独立页面）
退出游戏
```

行为：`StartMenu.handle_click` 返回 `"general_pool"` → `main.py` 调
`favorite_generals.on_enter(game, preferences)` 并把 `game.scene` 切成
`"general_pool"`。**没有重写菜单框架**，只是加了一个按钮 + 一个场景分支。
菜单底部还有一行摘要（"武将池：20 名武将" / "武将池：未配置（默认使用全部武将）"），
不用进页面就知道自己配过没有。

## 2. Favorite Pool 数据保存在哪里

`src/settings/preferences.py`，落在**仓库根目录的 `user_preferences.json`**
（已加入 `.gitignore`）。它是第一份"本机长期配置"，之前项目没有任何用户级
配置文件，所以这是一个**新的最小层**（不是复制第二套设置系统）。

```json
{ "version": 1, "favorite_generals": ["zhaoyun", "guanyu", "caocao"] }
```

* 只存 canonical general id（就是 `GeneralRegistry` 的 key，如 `zhaoyun`），
  **不复制 GeneralDef / 技能描述**；
* 不是 `Game` 的字段、不进存档、不进快照 / revision / DecisionRequest，
  也**不会**广播给其他玩家；
* 写入用"临时文件 + `os.replace`"，写一半断电不会把配置写坏；
* 文件损坏 / 顶层不是对象 → 退回默认值并继续跑（`load_error` 记录原因）；
* 探针可以把它指到别处：环境变量 `SGS_PREFERENCES`（不碰玩家真实配置）。

## 3. 第一次启动的默认池是什么

**当前全部可用武将**（按当前模式过滤：`game.playable_generals(for_random=True)`，
现在 84 名）。没有配置文件 → `favorite_generals` 为空元组 → 候选池回退到
"全部可用武将"，页面第一次进来也是全选状态。

用户**一旦保存过**，配置就以那份为准；之后新增武将**不会**自动塞进池子
（`has_favorite_generals()` 区分"没配过"与"配过且为空"）。

## 4. 当前最少允许多少名武将

**5 名**（`src/game/generals/draft.py::MIN_POOL = DRAFT_SIZE = 5`）。
不足 5 名时：

* 页面上「保存」按钮不可用，点击被拦下并提示
  **"武将池至少需要 5 名武将，当前 N 名"** + 底部一行 "至少选择 5 名武将才能保存。"；
* 磁盘配置**保持原样**（不会写进一个不可用状态）；
* 即使有人在配置文件里手工写 3 个 id，候选池也会回退到全部可用武将，
  开局永远不会因为池子太小而失败。

## 5. 无效 / 已删除的武将 ID 怎么处理

三级过滤，全部静默 + 记录：

1. `Preferences.favorite_general_ids()` 只做格式整理（去空、去重、保序）；
2. `draft.clean_pool(ids, registry, available_ids)` 拿**真实注册表 + 当前模式
   可用集合**过滤：不存在的 id 丢掉，未实现 / 测试专用 / 模式不允许的也丢掉；
3. `resolve_pool()` 在过滤后不足 5 人时**回退到全部可用武将**。

`Game.candidate_pool_ids()` 与 `GeneralRegistry` 都不认识"已删除"这个概念，
所以旧配置最多只是少几条，不会崩。实测：池里塞一个"已删除的武将"仍正常开局。

## 6. 每局 5 个候选在哪里生成

**业务层**，不在界面里：`src/game/generals/draft.py`

```text
Game.candidate_pool_ids()      偏好 ∩ 当前模式可用（不足 5 → 全部可用）
Game.roll_general_candidates() → GeneralDraft.roll(pool, game.rng, size)
                                  ↑ 只抽一次，之后一直是这份结果
```

* 随机只发生在 `draft.roll_candidates()`（`rng.shuffle` + 切片，即
  `random.sample` 的等价物）；
* 单机：`begin_general_select()` / `confirm_identity()` 各调一次
  `roll_general_candidates()`，结果存进 `game.general_candidates` 与
  `game.general_draft`；
* 联机：房主 `HostMatch._roll_for()` 生成（客户端只上传偏好，不自己抽）；
* **Renderer / draw() / update() 里一行随机都没有**——这是需求 §11 的硬约束。

每局候选数量 = `mode.general_choice_count`，本阶段从 3 改成 **5**
（`modes/base.py`、`modes/ffa.py`、`modes/identity.py`）。

## 7. 同一局候选会不会因为重绘而变化

**不会**。三道保障：

1. `GeneralDraft.roll()` 只真正抽一次（`if self.candidates: return`），
   重复调用返回同一份；
2. `Game.reset()` 会清掉 draft（换局才重新抽）；
3. 选将屏只**读** `game.selectable_generals()`，draw 里没有任何随机。

实测（UI 探针 G）：四档分辨率各 re-layout + 重画一遍，
`game.general_candidates` 与屏幕上显示的 5 张完全不变。

## 8. AI 是否受 Favorite Pool 限制

**不受**。两个池子严格分开：

```text
general_pool_ids()      全场共用（AI 分配、随机分配都用它）
candidate_pool_ids()    只有本机真人的**候选**用它
```

实测：玩家池子只有 5 名时，一桌 AI 仍然拿到 `weiyan / chengong / fazheng / zhouyu`
等池外武将，且同一局不重复。

## 9. LAN Host / Client 如何处理各自的武将池

**各自的偏好只影响各自的候选**，房主始终是候选的生成者：

```text
Client  ──FAVORITE_POOL{general_ids}──▶ Host      （新增消息类型）
Host 校验：id 真实存在 + 当前模式可用 + 去重 + ≥5
        │  不合法 / 不足 5 → 丢弃并记一条 note（退回全体武将池）
        ▼
Host 用**这名玩家自己的池子**抽 5 个候选
        └──GENERAL_CANDIDATES──▶ Client
```

* 房主自己用本机 `Game.favorite_general_ids`（main.py 从偏好读入）；
* 候选在**下发的那一刻**才抽（远程玩家的偏好随 IDENTITY_READY 到达，
  开局就抽会抽到全体池——这一点在探针里真被抓到并修掉了）；
* 如果偏好比候选到得晚（或改过），只要他还没选，房主会按新池子重抽并重发
  （客户端收到新候选会把已选项清掉，提示"房主更新了候选武将，请重新选择"）；
* **不广播**任何人的完整武将池给其他人；别人只会看到最终选了谁。
* 两个人各自的池子抽到同一个武将时：先到先得，后来者的候选被**重抽并重发**
  （不重抽他会一直等一个永远不会被接受的回答 → 选将阶段卡死）。

实测（联机探针 13/13，真实 socket）：房主候选全部来自房主的 8 人池，客户端
候选全部来自客户端上传的 8 人池，两边交集为空；非法上传被忽略；不在候选里的
选将被拒；两边各自拿到自己选的武将。

## 10. 最终 general_id 由谁校验

三层，全部在房主：

1. `HostMatch.note_favorite_pool` —— 上传的**池子**要过
   `clean_pool` + `MIN_POOL`（冒充他人 player_id 的消息直接丢弃）；
2. `HostMatch.general_picked` —— **选择**必须在他自己的候选里，且没被别人选走；
3. `Game.assign_generals` / `Game.set_general` —— 落座前再过一遍
   `general_available()`（非法 id 不会让整局在绑技能时炸掉）。

客户端 `ClientMatch.pick_general` 也做了一次"必须在候选里"的前置检查，
但那只是省一次往返，**不是**权威判据。

## 18. 尚未解决的问题

1. **没有"换一批 / reroll"**：按需求本轮不做，5 个候选必须从中选一个。
2. **武将池页面没有筛选（按势力 / 包 / 搜索）**：84 名武将靠滚动找，
   按需求本轮不做搜索；以后加筛选只需要在页面上加一排按钮（数据层已经
   有 `by_kingdom` / `by_pack`）。
3. **池子上限没有限制**（可以全选 84）——按需求"默认全选"就是合法状态。
4. **LAN 候选重复**只能靠"先到先得 + 重抽"解决；两边池子完全相同时
   第二个人会看到一批新候选（体验上比卡死好，但会多一次选择）。
5. **偏好文件只有一份**（没有"多套配置"或导入导出）。
