## 0. 口径修正（上一版报告写错的地方）

上一版报告有三处硬错误，先纠正，再谈结论。它们不是数字抄错，而是**统计定义**
本身把不同性质的东西混在了一起：

| 上一版的写法 | 事实 | 本报告的口径 |
| --- | --- | --- |
| "``hold=yes`` **200 局**出现" | 200 是**去重后的"同类问题记录"条数**（跨局累加），不是局数；100 局里没有任何一类问题出现在 200 局里 | 点击级计数与"问题记录条数"分列，互不换算 |
| "无效点击 6840 次（点了状态没变）"，并把 ``hold/busy`` 的局数加总到 227+200+33 | 6840 是"状态没变"的**点击**数；227/200/33 是"被谁挡住"的**去重问题记录**数。两者不是同一个单位 | ``blocked``（连路由都没进，``consumed=False``）与 ``consumed_no_effect``（被路由收下但局面没变）**分开计** |
| 把 ``consumed=True`` 当成"点击被接受了" | ``consumed`` 只说明**点击路由**收下了这一下；规则层完全可能拒绝它（引擎把原因写进 ``game.message`` 并取消动作） | 有效 / 收下但没效果 / 被拦，三类并列，且"被拦"按原因细分 |
| "seed 1：1597 次点击全部无效" | seed 1 实际只有 **1221 次点击、741 次状态没变**（原始 JSON 可查） | 引用数字一律以 JSON 为准 |
| 根因："选目标期间点击被演出让路吞掉，改 ``holds_local_input`` 即可" | ``holds_local_input`` 确实漏判本地槽位（独立缺陷，已修），但 seed 1 真正点不动的那一段，``presentation_gate.presenting=False``、``holds_local_input()=False``；拦住点击的是 ``storyboard.holds_interaction()``（当前演出是 ``SkillStep``） | 见第 2 节：四条独立根因，逐条复现 |

顺带纠正一个隐含口径：**"卡住 = 试玩工具宣布僵局"** 也不成立。旧脚本把
"等 AI / 等演出"与"真卡死"混着判，还用过 ``prev_sig`` 与当前帧比较，
演出正常播放期间局面本来就"没有变化"。新脚本只在本机玩家确实被要求回答、
或确实无事可等时，才允许宣布僵局；等演出期间**只记等待、不点击、不判僵局**。

## 1. 怎么跑的

``tools/soak_play.py``：SDL dummy 驱动 + 真实 ``Renderer`` + 真实点击入口。

主循环与 ``main.py`` 同序：

```text
game.update(dt)       推进引擎与动作队列
renderer.update(dt)   推进表现层（演出队列 / FX）
renderer.draw(game)   构建布局（点击命中依赖它）
观察局面 → 决策 → 点击 → 验证点击是否生效
```

4 路并行、每路 25 局，每局 rng 用种子播种，一局最多 9000 帧（30fps × 300 秒）。
玩家策略：能做就做最显然的事，**只在"本机被要求回答"或"轮到自己且有事可做"
时点击**；等别人 / 等演出期间不点击也不判僵局。

新脚本每局记录的字段（报告的数字全部取自这里）：

```text
clicks               投出去的总点击数
effective            点完局面状态变了
consumed_no_effect   被路由收下（consumed=True）但局面没变（**规则可能已拒绝**）
blocked.hold         被演出让路拦下      blocked.judge  被判定闸门拦下
blocked.busy         动画期间的乱点      blocked.no_hit 点在空处（策略问题）
waits.*              等待分类（帧数）：judge_logical / judge_presentation /
                     storyboard / presentation_gate / actions_busy /
                     others_turn / local_input
max_storyboard_lag   演出队列积压峰值
```

## 2. 复核：seed 1 到底为什么点不动

按你给的线索逐条复核，实测（``.cache/phase19/`` 下的取证脚本）结论如下。

### 2.1 seed 1 的点击确实被演出让路吞掉——但不是 ``holds_local_input``

第 314 帧起，``pending_target_selection`` 开着，点目标座位
``consumed=False hold=yes busy=False``，而当时：

```text
pg=0(-)                      PresentationGate.presenting=False → holds_local_input() 恒 False
jg=idle                      JudgeGate 空闲
sb_cur=skill!ui!key          Storyboard 当前是 SkillStep（holds_ui=True）
hold=1                       Effects.interaction_hold() = storyboard.holds_interaction() = True
```

**拦住点击的是 ``storyboard.holds_interaction()``**，它当初的语义是"技能提示
播完之前操作界面先别出现"，判据却只问"当前演出是不是压界面的技能提示"，
不问"本机玩家是不是正被要求做事"。

但**单改这一处也修不好 seed 1**——因为同一个局面里还有一个规则层的死循环。

### 2.2 seed 1 真正打不完的原因：一张【铁索连环】永远用不完

顺着"为什么一直在选目标"追下去，发现整局在做同一件事的循环：

```text
[出牌@101帧] 玩家 用 铁索连环 打 ['玩家']
[原子@101帧] MoveCardAtom 铁索连环 → 弃牌堆
      ### 牌被 append 回手牌：
        skills/expansions/yijiang.py:589, in resolve
          self.owner.hand.append(card)
```

曹植【落英】"其他角色的梅花牌因弃置或判定进入弃牌堆时可以获得之"，在
``resolve`` 里把自己刚用掉的【铁索连环】（梅花）**收回手里**。原因是
``CARD_DISCARDED`` 的 ``owner`` 查不出来：

* 使用结算后的牌走"手牌 → 处理区（``game.processing_zone``）→ 弃牌堆"；
* ``owner_of_zone(处理区)`` 不属于任何角色 → ``payload["owner"] = None``；
* 旧的 ``can_trigger`` 只判断 ``owner is self.owner``，``None`` 直接放行。

于是同一张牌被无限次"使用 → 收回 → 再使用"，整局永远打不完；它同时不断
往演出队列里塞 ``card_used / chain / skill``，积压峰值 63 条，进一步把
"演出让路"拉长成几十秒。

官方口径（``docs``/技能描述两处一致，另查官方 FAQ 印证）：【落英】只认
**因弃置或判定**进入弃牌堆，**使用、打出、重铸、拼点**都不算，无主的牌
（五谷没人要的牌、不屈牌）也不算。

### 2.3 响应窗口 ``consumed=True`` 却没效果：``busy`` 直接 return

复现（``_response_scene`` 用例）：响应窗口开着、动作队列在播动画时

```python
# src/game/combat.py（旧）
def respond_with_card(self, index, source_rect):
    if self.busy:
        return              # ← 点击被路由收下（consumed=True），规则层什么也没做
```

同一条链上还有两处把"队列忙"当成"轮不到我回答"：

* ``card_action_session.current_card_action_context()`` 在 busy 时返回 None
  （于是连"这张牌能不能响应"都问不出来）；
* ``Game.pass_response()`` 同样在 busy 时直接返回。

### 2.4 判定演出期间的输入被压住（本轮新发现）

seed 6 / 23 / 79 的失败形态是 ``blocked.judge``：

```text
点击被拦(本机被问) | 选牌 consumed=False 原因=judge=presentation
  被问=pending_request+pending_selection pending=request=select_cards/ganglie
```

判定**规则上**已经走完、只剩面板还在演时，``JudgeGate`` 把本机玩家的输入
全拦（原设计："判定牌还在屏幕中央时别让玩家出下一张牌"）。但这次判定带出的
后续请求（【刚烈】弃牌、遗计分配…）正等着本机玩家回答，压住它就只剩干等
（实测连续 240 帧、57 次点击全被吞）。

### 2.5 手牌命中：布局过期时确实会点到"另一张牌"

``Renderer.card_at_position`` 旧逻辑要求 ``len(table_layout.hand_rects) == len(hand)``
才用已绘制的 rect，否则退回 ``_fallback_hit``（按**当前**张数现算一套坐标）。
真实事件顺序下这会在这几种情况下触发：手牌刚被打出 / 刚摸到（张数变了）、
同一帧连续点击、以及布局还没画过的首帧。此时玩家点的是**屏幕上旧位置**的牌，
兜底公式给的却是"按新张数重排后的位置"——张数变化后它们不是同一张牌。

### 2.6 另外三个由这次的"同一张牌被反复使用"探针抓到的规则缺陷

* **无人能回答的请求会让整局挂起**（不是输入问题，但形态就是"点不动"）：
  * seed 51：【火攻】的目标在结算前失去全部手牌 → 生成
    ``select_cards/huogong_reveal``，候选为空却要求选 1 张，AI 与真人都答不了；
  * seed 55：【顺手牵羊】的目标区域在结算前被清空 → 同样空候选。
* **【丈八蛇矛】会被"能发动"骗进去**：``view_as_options`` 只验证单张素材，
  不看"两张牌凑起来的【杀】到底能不能用"。本回合已经出过【杀】时，玩家点
  武器 → 选满两张牌 → 提示"本回合已经使用过【杀】"，界面停在原地，只能
  点「取消技能」退出。脚本在这里复读 58 次，看起来像死局，其实是产品缺陷。
* **同一张牌画两处、只有一处能点**：【补益】让本机玩家展示**自己**的一张
  手牌时，这张牌同时出现在手牌区与公共池里；选牌界面只接受池子那一边的
  点击，点手牌那一份 ``consumed=True`` 但什么都不发生。

## 3. 改了什么

### 3.1 本地输入优先级（本轮主线）

新增**唯一**判据 ``src/game/contracts/local_input.py``：

```python
local_interaction_slots(game)   本机玩家此刻被要求做的所有事
                                （引擎请求 + 选目标 / 选牌 / 技能输入 /
                                  视为技来源 / 出牌方式 / 响应窗口 / 二选一）
local_awaiting_input(game)      上面那个是不是空的
local_response_live(game)       有没有一条仍然有效的响应请求在等我回答
request_targets_player(...)     这条请求问的是不是这个人
```

四处闸门改成读同一份判据（不再各判一半）：

| 位置 | 现在的规则 |
| --- | --- |
| ``PresentationGate.holds_local_input`` | 演出在飞时，**本机被要求做事就不让路**（原来只看 ``pending_request``，漏掉"出牌选目标"这类本地槽位） |
| ``ui.storyboard.holds_interaction`` | 同上：压界面的技能提示也**不让路**（seed 1 的直接拦截点） |
| ``Effects.interaction_hold`` | 组合上面两条，并新增 ``hold_source()`` 供日志/报告说明是哪一层在挡 |
| ``JudgeGate.allows_local_input`` | 三层判据：① 判定自己的输入永远放行；② **规则上**判定没走完 → 只放行①；③ 只剩画面在演 → 本机被要求做事就放行，否则拦 |

响应窗口（fact 2）：

* ``CombatMixin.respond_with_card / pass_response``：队列忙时**不再直接 return**，
  改为"本机确实还有一条活着的响应请求"就放行（``local_response_live``）；
  牌名、牌所在区域、请求 id、回答者身份仍然由引擎 ``_respond_card`` 复核，
  面板提交时先清空自己、引擎按 request_id 取走请求 → **只结算一次**；
* ``card_action_session``：``current_card_action_context / begin_card_action /
  card_action_options / _begin_with_options / _resolve_card_action`` 增加
  ``allow_busy`` 关键字，**只给响应窗口这一条路径**开；普通出牌 / 弃牌仍然
  要求队列空（未全局取消 busy 限制，用例 2.3 专门守着这条）。

### 3.2 手牌命中（fact 3）

* ``ui/layout.py``：``TableLayout`` 记下这份布局**是为哪几张牌画的**
  （``hand_cards``），新增 ``hand_card_at(position, hand)``：先按被绘制出来的
  rect / 上浮 rect 命中，再按**牌的身份**换算成当前下标；
* ``Renderer.card_at_position``：只要布局属于同一局、同一份手牌，就用它命中。
  点到的牌已经不在手牌里 → **不命中**（不再顺手选中"现在占这个位置的另一张牌"）；
  只有"根本没有可用布局"（首帧尚未绘制 / 布局属于另一个 Game）才退回兜底。

### 3.3 【落英】与弃牌事件的归属（seed 1 的真正根因）

* ``MoveCardAtom`` 新增 ``owner`` 字段，``_notify_discard / _notify_lost`` 优先
  用它（处理区查不出归属，必须显式给）；
* 在使用 / 打出 / 判定 / 拼点 / 装备替换这些"非弃置"的移动点上标注
  ``reason`` 与 ``owner``：``use`` / ``respond`` / ``judge`` / ``pindian``；
* 曹植【落英】改为只认 ``discard`` + ``judge``，且必须**归属明确且不是我自己的**。

### 3.4 另外三处规则缺陷

* 【火攻】【顺手牵羊】：目标在结算前把牌交光时**作罢**，不再创建空候选的
  选牌请求；
* 【丈八蛇矛】等视为技入口：新增 ``CardActionDiscovery.usable_combination``，
  "素材凑得齐"之外还要"有一组真能提交"，否则直接把原因写进提示、不进选牌模式；
* 【补益】式"展示自己的手牌"：公共池里的候选如果同时是本机手牌，点手牌那一份
  同样算选择。

### 3.5 试玩脚本（先修仪器，再谈效果）

* 统计口径按第 0 节重写：``blocked``（按 hold / judge / busy / no_hit 分类）
  与 ``consumed_no_effect`` 分列；
* 停止条件：只在"本机被要求回答却推不动"或"无事可等也推不动"时判死局；
  **等演出 / 等别人不点击、不判僵局**；等待上限随当前演出积压增长
  （队列压着几十条演出时，光播完就要几十秒）；
* 新增常驻探针：**同一张牌被反复"使用完成"**（规则没收走牌）、
  **无人能回答的请求**（候选为空却要求选 ≥1 张）；
* 策略补全：会点"发动技能"走转化（响应窗口里也能），会点武器技能、会在
  视为技选满却用不了时点「取消技能」退出，记住"同一局面下点过没反应的动作"
  不再复读；``SOAK_MAX_FRAMES`` 可放大帧数上限（区分"真卡住"与"只是慢"）。

## 6. 未完成局的逐条分类（这一节就是你要的"分别是哪种问题"）

修复后 100 局里有 11 局没打完，**没有一局是产品缺陷**：

| 分类 | 局数 | 种子 | 判据 |
| --- | --- | --- | --- |
| **帧数上限（节奏）** | 8 | 4、5、11、51、61、64、71、100 | 点击全部有效、无死局、状态持续推进，只是 300 秒游戏时间内没分出胜负 |
| **正常等待（演出太长）** | 3 | 10、28、62 | 全程在等演出 / 等 AI，脚本按设计"等别人时不点击"，超过等待上限后结束 |
| 产品问题（输入） | 0 | — | — |
| 产品问题（规则） | 0 | — | — |
| 试玩策略问题 | 0 | — | — |

**帧数上限的 8 局不是"卡住"的证据**：把上限放大到 24000 帧（≈13 分钟游戏时间）
重跑，4、5、61、71 打完（1395 / 7074 / 13357 / 9847 帧），11、51、64、100 仍然
打不完——那是"这局实在太长"（AI 之间互相打不死 + 每次结算都有完整演出），
不是点不动。所以在 9000 帧的口径下把它们记成"帧数上限"，在报告里必须与
"死局"分开读。

**正常等待的 3 局**：等待内容都是 ``judge_presentation + storyboard +
presentation_gate + actions_busy (+ others_turn)``，演出积压 2–48 条。
这是"规则跑得比演出快"的必然结果——脚本每 3 帧就能点一次，AI 也在全速结算，
而每条演出要占 0.5–2 秒画面。真人玩不会积压这么多，但**积压本身要有个出口**：
这一轮的出口是"本机被要求做事时演出一律让开"（3.1），所以积压再长也不会
再吞点击。

## 7. 遗留问题（本轮没做，已知，不影响上面的结论）

1. **演出积压没有上限之外的处理**：队列超过 64 条会丢非关键演出，但"积压 48 条
   = 画面落后一分钟"这件事本身没解决。真人玩不会这么夸张，批量试玩会。
   若要进一步压缩，可在"本机玩家无事可做且积压过大"时快进提示类演出。
2. **可选技能仍然自动发动**：``Skill.optional`` 字段存在但**无人使用**，
   【落英】一类"你可以获得之"的技能在真人这里是自动拿牌（本轮只修了"不该触发
   时触发"这一半）。要恢复"由玩家决定"，需要给技能触发加一个统一的确认窗口，
   属于系统级改动。
3. **AI 的随机源在非 1v1 模式下未播种**（已知问题）：所以同一颗种子在不同批次
   里偶尔会走出不同的局（第 5.2 节的两批数据里，未完成局的集合有小幅差异）。
   统计结论不受影响，但"逐位复现"还不成立。
4. **【丈八蛇矛】那类"看起来能发动"的入口**已加组合校验，但同类检查只覆盖了
   ``begin_view_as``；其它"先选素材再结算"的入口（多来源转化的主动技）建议
   统一走 ``usable_combination``。
